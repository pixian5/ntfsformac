1. **「记住密码」功能没有效果**（勾选「记住」后，重新插入加密盘不会自动解锁）
2. 守护进程日志被非 NTFS 分区的 `ntfs-3g` 失败刷屏（用户批准的优化：**挂载前 NTFS 签名预检**）

## 一、「记住密码」失效：三个叠加的根因

排查过程中逐一实证（`security find-generic-password -w | hexdump -C`、`security dump-keychain`、
App 侧文件日志），发现**三个**独立缺陷叠加，任何一个都会导致自动解锁失败。

### 根因 A（决定性）：`security` 会把含控制字符的值存成十六进制文本

旧版保存格式是 `<凭据>\n<方法码>`，即值里**含一个换行**：

```swift
// 旧版（错误）
security add-generic-password -s NTFSFormac -a <dev> -w "\(credential)\n\(methodCode(method))"
```

macOS 的 `security` CLI 在值含有**可打印 ASCII 之外的字节**时，
**会把值改存为该值的十六进制文本**，并且 `find -w` 读出来也返回那段十六进制文本。
实测（用 `hexdump -C` 逐字节确认）：

| 写入的值 | `find -w` 读回 | 是否被 hex 化 |
|---|---|---|
| `u99999999`（纯 ASCII 可打印） | `u99999999` | 否 ✔ |
| `99999999` + 换行 + `u` | `39393939393939390a75` | **是** ✘ |
| `ab` + 制表符 + `cd` | `6162096364` | **是** ✘ |
| `密码9999`（含中文多字节） | `e5af86e7a08139393939` | **是** ✘ |

而旧版格式 `<凭据>\n<方法码>` **必然含一个换行**，所以**每一条**保存的凭据都被 hex 化了
——「记住密码」此前是 100% 失效，不是偶发。解锁时把 `39393939393939390a75` 当密码传给 dislocker
→ 必然 MAC 校验失败。

附带结论：**含中文等非 ASCII 的密码**即便没有控制字符也会被 hex 化，所以修复必须覆盖所有字节，
不能只处理换行。

**修复**：把 `<方法码><凭据>` 的 UTF-8 字节**整体做十六进制编码**再存：

```swift
private func encodePayload(_ credential: String, method: UnlockMethod) -> String {
    let payload = Array((methodCode(method) + credential).utf8)   // 如 "u99999999"
    return payload.map { String(format: "%02x", $0) }.joined()     // "753939393939393939"
}
```

这样存入的是一段**纯 ASCII 十六进制文本**，`security` 不会再二次改写它；读取时解码即可。
方法码放在**最前**（`u`/`r`/`b`）+ 凭据，避免需要换行分隔。

读取端 `decodePayload` 兼容三种历史格式：
- 新格式 `<方法码><凭据>`（整体 hex）
- 旧格式 `<凭据>\n<方法码>`（被 security 二次 hex 过）
- 最旧格式：整串即凭据（按用户密码处理）

### 根因 B：钥匙串键用了设备名（`diskXsY`），每次插拔都会变

旧版 `saveCredential(for: device)` / `loadCredential(for: device)` 直接拿 `disk4s1` 当 account。
macOS 每次重新枚举磁盘，卷号都会变（`disk4s1` → `disk6s1`），**键变了自然查不到旧条目**。

**修复**：改用 **BitLocker 卷 GUID**（卷头里**明文可读**、与设备号无关、跨插拔稳定）：

- `ntfsctl` 新增 `bl_guid()`，按签名选偏移取 16 字节并还原 Windows 混序端序：
  - `-FVE-FS-`（经典 BitLocker）→ 卷头偏移 `0xa0`
  - `MSWIN4.1`（BitLocker-To-Go）→ 卷头偏移 `0x1a8`
- `ntfsctl list --porcelain` 新增**第 6 字段** `guid`（非 BitLocker 为空）：
  ```
  device|label|<ntfs|bitlocker>|mountpoint|<rw|ro|none|locked>|guid
  ```
- App 侧 `keychainAccount(for:)` 优先返回 GUID，无 GUID 才回退设备名；保存用 GUID 键并**顺带删除旧设备名条目**；
  读取**先 GUID、再回退设备名**（兼容 v0.0.11 及以前存的旧条目）。

**GUID 与设备号无关的决定性验证**：把同一份 BitLocker 镜像复制成两份副本，分别 attach 得到两个不同设备号，
读出的卷 GUID 完全一致。

### 根因 C：`autoTried` 标记时机错误

旧版在**读取凭据之前**就写入 `autoTried`：

```swift
// 旧版（错误）
if autoTried.contains(d.device) { continue }
autoTried.insert(d.device)                                    // ← 先标记
guard let (method, cred) = loadCredential(for: d.device) else { continue }   // 后读凭据
```

于是「第一次插入时（还没记住密码）」的盘会被本会话**永久标记为已尝试**，
之后即使保存了凭据（重新锁定再看）也永远不会再自动解锁。

**修复**：**先确认有凭据，才写入 `autoTried`**。

### 附带改进

- 新增 `appLog()`：写 `~/Library/Logs/NTFSFormac/app.log`（>1MB 自动截断），
  记录自动解锁的关键决策（设备/GUID/方法码/成功失败），**绝不记录凭据明文**，只记长度。
- 新增 `noCredChecked`：确无凭据的盘本会话不再每 3 秒重复查一次钥匙串（减少无谓 IO）。
- `saveCredential` 成功后清掉该盘的 `autoTried` / `noCredChecked` 标记。

### 设计说明：手动「重新锁定」后不会自动重新解锁（有意为之）

`autoTried` 是**内存态**、按卷 GUID 键记录。行为：

| 场景 | 结果 | 说明 |
|---|---|---|
| 插入加密盘（App 未见过的卷） | **自动解锁** | 键不在 `autoTried` 中 |
| 点「重新锁定」 | **保持锁定** | 键仍在 `autoTried` 中 → 尊重用户意图，否则「锁定」按钮将形同虚设 |
| 拔掉再插入 | **自动解锁** | 设备消失时 `autoTried` 按现存键求交集被清除 |

若希望「命令行 `ntfsctl lock` 也不会被 App 在 3 秒内自动重挂」，可仿照 `ejecting.<dev>` 引入
`lock.<dev>` 标记（60s TTL）——**本轮未做**，因为 App 菜单的「重新锁定」路径已正确，
且标记放 `/var/run/ntfsformac/`（root 属主）而 App 以用户身份运行，读取需额外的免密通道。列为可选优化。

### 端到端验证（真实 U 盘 disk4s1，exFAT 内层，密码 99999999）

```
list: disk4s1|BitLocker-disk4s1|bitlocker||locked|4967D63B-2E29-4AD8-8399-F6A339E3D001
app.log: readCredential(4967D63B-...) 解析结果=method=u credLen=8
app.log: disk4s1 guid=4967D63B-... 找到凭据 method=u，尝试自动解锁
app.log: disk4s1 自动解锁成功
list: disk4s1|Ventoy15.1|bitlocker|/Volumes/Ventoy15.1|rw|4967D63B-...
```

钥匙串里最终只剩一条按 GUID 的条目（旧设备名条目已清）。

## 二、挂载前 NTFS 签名预检

### 背景

`ntfs_devices` 用 `diskutil list` 的 `Microsoft Basic Data` 等宽松关键字匹配，
会把**非 NTFS 的分区**（例如 BitLocker 解密卷附加出的镜像设备、其它杂项分区）也列为候选。
旧行为是直接丢给 `ntfs-3g` → 必然失败 → 守护进程每 3 秒重试一次，**日志被刷屏**（实测 2273+ 行）。

### 实现

在 `mount_one` 的**非 BitLocker 分支**（`is_bitlocker` 判断**之后**、调用 `ntfs-3g` 之前）读首扇区校验签名：

```bash
local fsig_hex
fsig_hex=$(as_root_np dd if="/dev/$dev" bs=512 count=1 2>/dev/null \
           | head -c 11 | tail -c 8 | od -An -tx1 -v | tr -d ' \n')
if [ -n "$fsig_hex" ] && [ "$fsig_hex" != "4e54465320202020" ]; then   # "NTFS    "
  log "跳过 ${dev}：首扇区签名非 NTFS（hex=${fsig_hex}），不做无效挂载"
  return 0
fi
```

要点：

- **只读 8 字节比对，用 `od` 取十六进制串**，不经 shell 变量承载原始字节——
  非 NTFS 分区该处常含 NUL 字节，bash 命令替换会丢弃它们并刷 `warning: command substitution` 类噪音。
- **`return 0` 而非 `die`**：守护进程不把「正常的跳过」当错误。
- **必须放在非 BitLocker 分支**：BitLocker 卷的首扇区是 `-FVE-FS-`，放在前面会把所有加密盘都跳过。

### 【关键】读到空时必须继续尝试挂载（fail-open），不能跳过

最初按「读不到也跳过」（fail-closed）实现，`test-automount.sh` **立刻失败**：

```
自动挂载读写: disk25s1 (AUTOTEST, state=ro)
[ntfsctl] 跳过 disk25s1：首扇区签名非 NTFS（hex=空）      ← 错！
```

原因：卷**已被 macOS/FSKit 只读挂载**时，裸设备读取会因 `EBUSY` 失败（读到空）。
而这恰恰是最需要抢挂成读写的场景——Tahoe 上 FSKit 会把 NTFS 挂成只读寄生虫。
按 fail-closed 处理，**只读抢占将永远无法纠正**。

故改为：**只有「确实读到了签名、且签名不是 NTFS」才跳过**；读到空（EBUSY / 刚移除）
一律继续走正常挂载流程。实测改后 `test-automount.sh` 7/0 全绿。

## 三、附带的 bash 坑：`$var` 紧跟多字节字符会吞掉变量名

新增日志 `"跳过 $dev：首扇区签名非 NTFS"` 输出成了 `跳过 ：首扇区签名非 NTFS`——`$dev` 丢了。
原因是 `$dev` 后面紧跟**全角冒号**（多字节 UTF-8），bash 解析变量名时把后续字节也算进去。

**教训**：变量后紧跟多字节字符时，一律用 `${var}` 界定：

```bash
log "跳过 ${dev}：..."        # 对
die "$dev 解密卷内层文件系统为 ${ifs}，暂不支持挂载"   # 对（$dev 后是空格，可省；仍统一加花括号）
log "已导出到 ${DOUT}（...）"  # 对
```

本轮审计并修掉了 `ntfsctl` 中全部「`$var` 后紧跟多字节字符」的写法。

## 四、验证中发现的新问题：`lock` 未持互斥锁（→ v0.0.13）

验证「新插入自动解锁」时一度出现**假成功**：App 日志明确写着「自动解锁成功」，
但 2 秒后查询卷状态又是 `locked`，且 `dislocker-fuse` 进程数为 0。

排查：当时我的测试脚本**紧接着**发起了一条 `ntfsctl lock`，与 App 的自动解锁**并发**了。
而 `bl_lock_one` 当时**没有**走 `lock_mount` 互斥锁（对比：`bl_unlock_one`、`mount_one` 都走了）：

```bash
# 旧版（错误）—— lock 不持锁，可与 unlock 并发
bl_lock_one() {
  is_bitlocker "$dev" || ...
  label=$(bl_label "$dev"); mp=$(mountpoint_of ...)
  [ -n "$mp" ] && unmount_one "$dev"
  bl_close_container "$dev"     # ← 可能拆掉另一进程刚挂好的 dislocker-fuse 容器
}
```

后果：`bl_close_container` 把刚建立的解密容器 SIGTERM/SIGKILL 掉，
于是「解锁报成功 → 随即回退 locked」。

**修复（v0.0.13）**：`bl_lock_one` 全程持有 `lock_mount`，并 `trap 'unlock_mount' EXIT` 兜底：

```bash
lock_mount || die "另一个挂载/解锁操作进行中，请稍后再试"
trap 'unlock_mount' EXIT
...
unlock_mount; trap - EXIT
```

**顺序化复测**（先等 lock 完成、再启动 App）：vol 稳定保持 `rw`，
在 +12s 与 +28s 两次采样均未回退，`dislocker-fuse` 恰好 1 个进程。

> 教训也能反向用：**看到「解锁成功又变回锁定」，先怀疑是不是有并发的 lock/eject**，
> 不要立刻当成密码或解析问题。这正是一开始误导我排查方向的原因。

**留待后续**：`eject_one` 同样会改动挂载态但仍未持锁（本轮未改，见「后续可选优化」）。
