## 一、两个核心 bug（本轮真正的根因）

### bug 1：卷已挂载时，缓冲设备读不出内容 → 被误判成「不认识 / 不能挂」

实测对照（同一个分区 disk4s1，**已挂载**状态）：

| 读取对象 | 命令 | 结果 |
|---|---|---|
| 缓冲设备 `/dev/disk4s1` | `dd bs=512 count=1` | `dd: Resource busy` → **0 字节** |
| **裸设备** `/dev/rdisk4s1` | `dd bs=512 count=1` | **512 字节，正常** |

后果链条：`fs_type_of()` 读不到首扇区 → 返回 `unreadable` → 新加的挂载前预检把该盘当成
「未知内容」直接跳过 → 用户看到的现象正是「分区明明插着，工具却说不出它是什么 / 不能用」。

**修复**：新增 `dev_io()`，所有内容读取与整分区导出统一走 `/dev/r<dev>`：

```bash
dev_io() {
  if [ -e "/dev/r$1" ]; then printf '/dev/r%s' "$1"; else printf '/dev/%s' "$1"; fi
}
```

覆盖点：`probe_one` / `fs_type_of` / `raw_label` / `exfat_label` / `is_bitlocker`（含消歧） /
`bl_guid` / `mount_one` 的签名预检 / `raw_mount_one` 的整分区导出。
（`dump` 子命令早在 v0.0.x 就用了 `/dev/r$DD`，本次是把其余路径补齐到同一规范。）

### bug 2：裸设备只接受扇区对齐读 → 字节粒度读必须换写法

修好 bug 1 之后，exFAT 卷标读不出来了。实测：

| 命令 | 结果 |
|---|---|
| `dd if=/dev/rdisk4 bs=1 skip=3 count=8` | **0 字节**（裸设备拒绝对齐以外的偏移） |
| `dd if=/dev/disk4  bs=1 skip=3 count=8` | 8 字节（缓冲设备支持字节读，但挂载时会 EBUSY） |

**修复**：新增 `dev_read_bytes(dev, off, len)` = 「按扇区对齐 dd + `tail -c`/`head -c` 切到目标字节区间」，
两种情况下都成立，且不需要判断卷是否挂载：

```bash
dev_read_bytes() {   # 用法: dev_read_bytes <dev> <字节偏移> <长度>
  local dev="$1" off="$2" len="$3" bs=512 first delta cnt
  first=$(( off / bs )); delta=$(( off - first * bs ))
  cnt=$(( (delta + len + bs - 1) / bs )); [ "$cnt" -ge 1 ] || cnt=1
  as_root_np dd if="$(dev_io "$dev")" bs=$bs skip="$first" count="$cnt" 2>/dev/null \
    | tail -c +$((delta + 1)) | head -c "$len"
}
```

`exfat_label()` 改用它读根目录的 0x83 卷标条目（原实现用 `dd bs=1`，正是这条 bug 的受害者）。

## 二、把「分区类型」与「分区内容」彻底解耦

此前 `ntfs_devices()` 只按分区类型（`Windows_NTFS` / `Microsoft Basic Data`）挑候选，
而 Windows 上格式化成 exFAT/FAT32 的分区，**分区类型同样常是 Microsoft Basic Data**。
于是会出现两种「不能用」：

| 情形 | 旧行为 | 新行为 |
|---|---|---|
| 分区类型是 NTFS/Basic Data，内容是 exFAT/FAT | 交给 ntfs-3g → 必然失败、守护日志刷屏 | 预检识别为 FAT 家族 → 自动改走只读镜像路径 |
| 分区内容是未知（非 NTFS/FAT） | 反复失败 | 明确告知「内容既不是 NTFS 也不是已知 FAT 家族，可用 `ntfsctl probe <dev>` 查看」 |
| 签名 `MSWIN4.1`（FAT 与 BitLocker-To-Go 共用） | 一律当 BitLocker → 显示「加密未解锁」、挂不上 | 两级消歧，见下 |

`MSWIN4.1` 消歧（实测 `dislocker-metadata` 对真 BitLocker 返回 0、对 MSWIN4.1 的 FAT32 返回 1）：

1. BPB 里有明确 FAT 类型串（偏移 `0x52` FAT32 / `0x36` FAT12-16）→ 是普通 FAT 盘；
2. 否则问 dislocker 能否解析出 BitLocker 卷头（读元数据**不需要凭据**，加密盘也能读）。

`list` 的归并顺序也据此调整：**先判 BitLocker**（它自己会消歧），再按内容归类其它。

## 三、`list` 现在输出什么

`ntfs_devices` 仍是候选来源，但每条候选都会读首扇区重新归类，并且**额外**并入
`other_devices()`（外置物理盘上「未被原生挂载、内容是 FAT 家族」的分区）：

| fs 字段 | 含义 | 挂载方式 |
|---|---|---|
| `ntfs` | 真 NTFS | ntfs-3g 读写 |
| `bitlocker` | 加密卷（含未解锁 state=locked） | dislocker 链路，凭据由用户提供 |
| `fat12/16/32/exfat/fat` | FAT 家族 | **只读裸镜像**（副本，写入不回写原盘） |
| 其它 | 如实标注 | 不挂载，提示用 `probe` 查看 |

另外新增：

- `exfat_label()`：exFAT 卷标**不在 BPB 里**，而在根目录 0x83 卷标条目；按簇堆参数换算偏移
  （`字节偏移 = (簇堆偏移 + (根目录首簇号-2) × 每簇扇区数) × 每扇区字节数`）读出 UTF-16LE 卷标。
  实测输出 `EXXTEST` / `FAT32TST` 正确。此前这些分区只能显示成 `exfat-diskXsY`。
- `prune_raw_images()`：拔盘却没 eject 时，`/var/run/ntfsformac/raw-image/` 会残留记录与临时镜像。
  挂在 `list`（App 每 3 秒一次的心跳点）上清理：**原设备节点不存在**即摘镜像、删记录与文件；
  设备仍在的记录**保留**（测试专门覆盖了「不得误删在用记录」）。
- `probe` 现在额外打印卷标，排查「这个分区到底是哪个」时一眼可见。
- `raw_mount_one` 增加「macOS 已原生挂载就直接用」分支，避免同一内容挂两份（`VTOYEFI` / `VTOYEFI 1`）。

## 四、install-driver.sh 免密化（去掉管理员授权框）

原先两处 `osascript -e '... with administrator privileges'`（装 FUSE-T pkg、`make install`）
会弹管理员授权框。改造：

1. 把真正需要 root 的两步拆成**特权子命令** `--priv pkg` / `--priv make-install`，root 下直跑；
2. 非 root 时经 `priv()` → `sudo -n /bin/bash <SELF> --priv ...` 免密重入；
3. `scripts/install-service.sh` 的 sudoers 白名单新增一行（与 `test/*.sh*` 同款通配）：

```
<x> ALL=(ALL) NOPASSWD: /bin/bash /Users/x/code/ntfsformac/install-driver.sh*
```

**为什么不整个脚本重入 root**：脚本前半段的 brew 明确拒绝以 root 运行，构建产物也应归属用户；
真正需要 root 的只有最后的安装动作。

`--priv` 入口刻意放在「环境检查」之前 —— 重入后 root 的 PATH 里通常没有 brew，
若先跑环境检查会被误判「缺 Homebrew」而失败。

**实测**（以普通用户 `x`、无 sudo 前缀、零弹窗）：

| 命令 | 输出 | 判定 |
|---|---|---|
| `sudo -n ... /install-driver.sh --priv bogus` | `错误: 未知特权子命令: bogus` | 白名单已放行（若未放行会是 `a password is required`） |
| `--priv pkg`（缺参数） | `错误: 特权子命令 pkg 缺少包路径` | 参数校验生效 |
| `--priv make-install /tmp/nope-xyz` | `错误: 构建目录不存在` | 参数校验生效 |

> App 侧无需改动：`检查驱动更新` 现在只**提示**用户在终端运行 `install-driver.sh`，并不自行调用。

## 六、诚实的覆盖边界（哪些情况仍不支持）

| 情形 | 现状 |
|---|---|
| 外置物理盘上的 FAT 家族分区（FAT12/16/32、exFAT） | **已支持**：可见 + 只读浏览 |
| 内置于 macOS 原生已能挂载的分区（如 exFAT 可识别） | 直接用原生挂载点，不建副本 |
| 内容为 ext4 / HFS+ / 未知格式 | **不支持**：会如实提示「既不是 NTFS 也不是已知 FAT 家族」，不尝试挂载 |
| 内置盘（internal）的其它分区 | **不收录**：`other_devices` 只取外置盘（`diskutil list` 的 `external` 标记） |
| 已挂载的其它分区 | **不重复列出**（避免与原生挂载重复，噪音） |
| 只读副本的写入 | 明确不支持（副本语义），需要写入请在 Windows 操作 |

## 十、答疑：BitLocker 分区「回写」是否需要整分区逐字节写回？

**结论：不需要。** 只回写「实际改动过的扇区」，未改动区域一个字节都不碰。

### 为什么

两条「只读/回写」路径的性质完全不同，不能混为一谈：

| | 「其它分区」（如 VTOYEFI） | BitLocker 分区（如 Ventoy15.1） |
|---|---|---|
| 挂的是什么 | **dd 出来的静态副本**（`raw-image/<dev>.img`） | dislocker-fuse 暴露的**实时解密视图**（`bl/<dev>/dislocker-file`） |
| 与后端关系 | 副本与原盘**无任何通道**，写副本 ≠ 写原盘 | FUSE 读写**直达后端**：`-V /dev/disk4s1` |
| 挂载方式 | `hdiutil attach -readonly`（强制只读） | `hdiutil attach`（可写，且 dislocker **未加** `-r`） |
| 写入语义 | 被 macOS 拒绝（`Read-only file system`） | 实时加密后写回原盘对应扇区 |

之前说的「整分区逐字节回写」风险，只适用于**第一条路径**（若给静态副本加「写回同步」，那才需要整份写回）。
BitLocker 走的是第二条：**不是拷贝，而是实时解密层**。

### BitLocker（FVE）为什么能按扇区增量写入

BitLocker 的整卷加密（FVE, Full Volume Encryption）采用**按「数据单元」（data unit，默认 512B~64KB）独立加解密**：

- 每个数据单元用 **FVEK**（全卷加密密钥）+ **自身在卷内的偏移量作为 tweak**，做 **AES-XTS**（旧版为 AES-CBC + Elephant diffuser）加解密；
- 因此每个数据单元的解密**只依赖该单元自己的密文与偏移**，与邻居无关；
- 改一个扇区 → 只重新加密该扇区 → 写回原盘对应偏移；**其他扇区密文保持不变，解密结果也不变**。

dislocker-fuse 正是利用这一点：它把加密设备当 backing store，读时按需解密、写时按需加密回写，
所以不需要任何「整分区临时文件」。（`du` 对该虚拟文件显示 15G 是 FUSE/NFS 层上报的 `st_blocks`，
并非真实分配——它并没有在磁盘上摊开一份 15GB 明文副本。）

### 实测佐证

- dislocker-fuse 实际调用：`dislocker-fuse -V /dev/disk4s1 -uXXXX -- /var/run/ntfsformac/bl/disk4s1`
  —— **无 `-r`**（该选项语义是「禁止写入 BitLocker 卷」），确认读写模式。
- 挂载链：`fuse-t:/disk4s1 on /private/var/run/ntfsformac/bl/disk4s1 (nfs)` →
  `hdiutil` 把该目录下的 `dislocker-file` 附加成 `/dev/disk24` → `/Volumes/Ventoy15.1 (exfat, fskit, rw)`。
- 写回可靠性（上一轮 v0.0.11 已在物理 BitLocker 盘验证）：解锁 → 写入 8MB → 卸载 → 重新解锁 →
  数据仍在（证明确实加密写回了原盘，而非仅停留在缓存）。
- 本轮 `ntfsctl` 源码中的刷盘注释也印证了这条写回链：
  「FUSE-T 为写回缓存，确保 ntfs-3g 已写入 dislocker-file 的数据落到后端设备」。

## 十一、BitLocker 读写往返验证（真实盘 Ventoy 15.1，2026-10-15 22:33）

应要求做端到端验证：**写入文件 → 加密落盘 → 重新锁定拆解密层 → 重新解锁 → 校验数据是否完好**。

### 测试路径设计（关键：全程无需用户输入凭据、零弹窗）

难点：重新解锁需要密钥，而钥匙串里的凭据只有 App 本人能读——若用 CLI 的 `security` 去取，
会触发钥匙串授权框（违反「严禁出授权框」）。于是**借道 App 自身的自动解锁能力**：

1. 写入数据 + `shasum -a 256` 清单（卷内留一份、本地 `/tmp` 留一份）
2. `ntfsctl lock disk4s1` → 强制刷盘、卸载卷、**停掉 dislocker-fuse**（解密层彻底拆除）
3. 结束 App —— 必须做：本会话的 `autoTried` 集合不清空的话，它不会对同一卷二次自动解锁
4. 以 root 删掉 `locked.disk4s1` 标记（借道白名单内的 `test/*.sh*`）
5. 重新 `open` App → 走**钥匙串自动解锁**
6. 逐文件 `shasum -a 256` 比对

### 结果

| # | 项目 | 结果 |
|---|---|---|
| 1 | 写入 4 个文件（1B / 4KB / 1MB / 8MB）+ 校验清单 | ✅ |
| 2 | `ntfsctl lock` 后：卷卸载、`dislocker-fuse` 进程退出、容器挂载消失、`locked.disk4s1` 标记落盘 | ✅ |
| 3 | 重启 App 后 **2 秒内自动解锁**（app.log：`找到凭据 method=u … 自动解锁成功`），零弹窗 | ✅ |
| 4 | 重新解密后 4 个文件 sha256 **全部一致** | ✅ |
| 5 | 第二轮：重解锁后**仍可写**（新写 2MB 文件） | ✅ |
| 6 | 第二轮再锁定 / 再解锁：5 个文件 sha256 **全部一致** | ✅ |
| 7 | 清理测试目录后卷根目录恢复原样（用户原有 docx 文件未受影响） | ✅ |

### 结论

**写入的数据确实以密文落在加密分区上，且可反复解密还原** —— 这是「按扇区增量回写」的端到端证明：
在 `dislocker-fuse` 已停止、卷完全不可访问的那段时间里，数据**只存在于密文分区中**。

### 一个不可用的「假证据」（避免以后误用）

`diskutil info disk4s1` 会报 `File System Personality: ExFAT`，**即使在锁定、无解密层的状态下也照样这么报**
（DiskArbitration 的探测/缓存产物）。所以它**不能**用来判断盘上是密文还是明文。
可靠判据是首扇区签名：偏移 3 起 8 字节为 `-FVE-FS-` 才是 BitLocker（普通 exFAT 该处是 `EXFAT␣␣␣`）。

可选强化（未做）：对整块加密分区做全量明文串扫描（约 16.3GB 读），可给出「明文确实不出现在盘上」的强证明。
