## P0（近期建议，价值最高）

### 1. 真实 U 盘 BitLocker 压测（v0.0.11 已完成 exFAT 主流场景）
- **已完成**：真实 U 盘（disk4s1 = Ventoy15.1，内层 **exFAT**）端到端跑通 —— 解锁 → 挂载读写 →
  8MB 写入并 SHA-256 校验一致 → 卸载/重挂（不重复附加镜像）→ lock 无残留 → 再解锁数据仍在 → 安全弹出。
  过程中修掉两个真实缺陷：dislocker 未知 datum 中断遍历（v0.0.10）、内层 exFAT 无法用 ntfs-3g 挂载（v0.0.11）。
- **尚未覆盖**：
  1. BitLocker **内层为 NTFS** 的**物理** U 盘/移动硬盘（镜像盘已通，物理盘未有样本）；
  2. 压力场景：大文件（>4GB）写入、热插拔、中途断电、写入时拔出；
  3. 同一盘上同时存在 BitLocker 卷 + 普通 NTFS 卷的混合场景。
- **方案**：拿到样本后跑
  `sudo bash test/test-bitlocker.sh --device diskXsY --password-file /path/pw`（或 `--recovery` / `--bek`）。
- **价值**：发现镜像盘/单一样本测不出的问题（USB 层供电、缓存刷盘时机、FS 混装）。

## 与既有要求的冲突提示

- **#2 pkg 安装器** 会引入 `pkgbuild`/`productbuild` 构建链，与当前轻量 shell 构建并存，安装流程从"跑脚本"变为"装 pkg"，**需你确认接受**（已表示接受）。
- **sudoers 收敛 vs 零弹窗**：曾因 sudo 1.9 参数完全匹配导致带参调用重新弹框，已通过「零参数调用 + 测试脚本 `*` 通配」解决；
  你已确认**白名单可以放宽**。当前 `ntfsctl` + 固定路径脚本 + 测试脚本通配，App 日常操作全走 `ntfsctl`，**零弹窗已验证成立**。

### 11. BitLocker 元数据解析加固（v0.0.10 已做基础版，可继续）
- **已做**：未知 value_type 的 datum 改为跳过而非中断遍历；新增 `info -v` / `dump` / `unlock --verbose`。
- **可继续**：移植上游 master 的 `find_virtualization_linear_from_metafile()` 线性扫描兜底
  （应对 datum 位于 64KiB 元数据副本尾部、被数据集边界迭代漏掉的情况）；
  以及为 entry/value 未知的 datum 建立"已知类型名"映射，提升 `info -v` 可读性。

### 12. 挂载态操作的互斥锁收口（v0.0.13 已修 `lock`，`eject` 待做）
- **已做（v0.0.13）**：`bl_lock_one` 纳入 `lock_mount` 互斥锁，消除「解锁报成功、随即回退 locked」的假成功
  （`bl_unlock_one` / `mount_one` 早已持锁，唯独 `lock` 漏了）。
- **待做**：`eject_one` 同样会改动挂载态但**仍未持锁**，应与 `mount`/`unmount`/`lock` 统一串行化，
  否则弹出可与挂载并发、造成挂载点/容器与弹出互相踩踏。
- **建议**：把「凡改动同一设备挂载态的子命令都必须持 `lock_mount`」作为一条硬约束补进 known-issues。

### 13. 可选：让命令行 `ntfsctl lock` 不被 App 自动重挂
- **背景**：App 的「重新锁定」菜单项路径已正确（该盘本会话不再自动解锁）。
  但从终端跑 `ntfsctl lock` 时，App 会在 3 秒内用记住的凭据把它重新解锁——对命令行用户略显意外。
- **方案**：在 `ntfsctl lock` 里写 `lock.<dev>` 标记（仿 `ejecting.<dev>`，60s TTL），App 见到标记则跳过自动解锁。
- **难点**：标记位于 `/var/run/ntfsformac/`（root 属主），App 以用户身份运行读不到，
  需借 `ntfsctl list` 把该状态返回（如状态值 `locked-manual`），避免新增免密通道。
- **需你确认是否有必要**（若你只用 App 菜单操作，可不做）。
